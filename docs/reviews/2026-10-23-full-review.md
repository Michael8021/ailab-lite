# 全量代码审查与修复（2026-10-23）

审查基线：`f45b12a`（main）。目标是修正可复现的逻辑错误，保持现有 lite/dev 架构；验收覆盖性能、健壮性、可维护性、简单性和可测试性。工作开始时工作区干净。

## 范围与方式

静态审查覆盖 Platform API、Agent、Broker、Worker、共享内核、迁移、Portal 的代理/认证/对话/文件/技能、部署脚本与清单，以及沙箱适配器和办公生成脚本。图标/字体/生成的架构图等静态素材不作逐文件人工审查。依赖沿用锁定版本，未做依赖升级。

对核心新问题先编写回归测试，在修复前执行并观察失败，再修改实现。修复后执行 SQLite、PostgreSQL 16、真实 Redis、Portal 单元测试与浏览器 E2E；最终重新审查整个 diff。该复审由同一执行者完成，不代表独立评审者已批准。

## 已修复的问题

### P1：预签名上传可在扫描后被覆盖

`platform/ailab_platform/api/routes_files.py` 的 complete 原先直接接受签名 PUT 指向的对象。签名在 15 分钟内可复用，上传者能用新内容替换已扫描、已记录哈希的文件。

现在先复制成独立对象，再对固定版本计算大小和哈希、提交元数据。Worker 和后续下载只使用固定版本。复用旧 PUT 不再修改已接受文件。无效/超配额对象清理；暂时性存储错误保留重试机会。

### P1：部分文件入口绕过资料库配额，并发提交可能重复入账

预签名 complete 没有进入普通上传已有的每用户临界区；多个请求能同时通过检查。沙箱产物提交原先完全没有检查资料库总配额，重复提交的幂等查询也没有串行化。

complete、artifact 的检查与写入复用 `user_critical_section`，PostgreSQL 通过用户行锁跨进程串行化。相同产物的重试先命中已有记录，额满时仍可重试而不重复收费。新增内容超额则拒绝并清理 staging。

### P1：token 上限在工具执行后才检查，结束分支和恢复分支可绕过

`agent/loop.py` 原先在执行整批工具后检查 token，纯文字结束和 finish 分支会先退出；恢复执行又从零累计。

现在将已记录用量计入起点，每次模型响应记账后先检查上限，再决定执行工具或结束。收尾调用也检查用量，已有工作仍通过原有归档路径保留。一次上游调用本身仍可能越过剩余额度，无法事后撤回上游已消耗 token。

### P1：对话模式只是不提供工具，没有拒绝模型意外返回的工具调用

现在对话模式及不支持工具的模型若仍返回 tool_calls，直接终止该轮，不启动沙箱、不执行工具。

### P1：模型流无结束标志也被当作成功

`llm.py` 原先遇到正常 EOF 就返回拼装结果，截断的回答或工具参数可能被接受。现在必须看到 finish_reason 或 `[DONE]` 才接受完成，缺少两者时报告 incomplete。原有已输出文本后不自动重放的行为保持一致。

### P1：部署镜像校验比较了不同种类的 digest

`deploy.sh` 原先将 Docker `.Id` 与 `ctr images ls` 的 manifest digest 比较，正确导入也会失败。现在通过 `k3s crictl inspecti` 比较配置 digest。

依据：[containerd 的 image ID 来自配置 descriptor](https://github.com/containerd/containerd/blob/main/internal/cri/store/image/image.go)，[CRI ImageStatus 返回该 ID](https://github.com/containerd/containerd/blob/main/internal/cri/server/images/image_status.go)。隔离测试刻意让配置 digest 与 manifest digest 不同，验证不会再误拒。

### P1：kubectl apply 失败后继续执行部署

移除 apply 后的 `|| true`，失败立即停止。命令替身测试验证失败不会被当成成功；测试不连接集群。

### P2：就绪探针不能反映实际不可服务状态

Agent/Worker 即使消费循环已退出，readyz 原先仍可能报告 ok；Broker 依赖不可用也返回 HTTP 200，清单又只探测 healthz。

三个服务现在返回对应的 HTTP 503，清单四个业务服务使用 readyz。Broker 每次仅检查一次 provider，探针超时设为 10 秒以覆盖现有外部健康检查。存活探针继续使用 healthz。

### P2：纯空白提示词造成 500

`prompt.strip().splitlines()[0]` 对空白输入越界。RunCreate/MessageCreate 共享非空白验证，进入业务逻辑前返回 422。

### P2：技能开关并发更新互相覆盖

两个请求从旧 settings 分别修改不同开关，后一次写入丢掉前一次。现在在每用户临界区内刷新用户记录后修改；并发关闭 PPT 和 Excel 的测试验证两个状态均保留。

### P2：删文件后仍保留提取出的明文

删除原文件和 derived meta 时遗漏 `text_key`，资料库删除后全文仍留在对象存储。现在一并清理。

### P2：下载文件名能生成非法响应头

ASCII fallback 原样拼接双引号与控制字符。现在过滤控制字符并转义 quoted-string，原始 Unicode 名通过编码参数保留。

### P2：SQLite 时间没有时区，界面在香港时区显示“8 小时前”

SQLite 读回 datetime 时丢失 tzinfo；浏览器将不带时区的 ISO 字符串按本地时间解析。现在在响应 schema 统一输出明确 UTC，PostgreSQL 的带偏移时间也归一化为 UTC；覆盖对话、任务、文件和事件。

### P2：侧栏轮询产生 N+1 数据库往返

列表原先对每条对话单查最后任务状态，回答期间浏览器每 4 秒重复。现在用一个查询带出相关标量子查询，并在相同创建时间时以 id 稳定排序。包括鉴权在内，回归测试要求列表请求最多 3 条 SELECT。数据库仍需处理各对话的相关子查询，这不是数据规模无关的计算成本承诺。

### P2：对话页面异步响应和流没有完整管理生命周期

较旧详情响应可覆盖较新的结束状态；初始请求结束前离开页面仍可能启动流；发送新轮时建立的流不受初始 effect 的 controller 管理。

现在用请求序号拒绝旧响应，统一持有当前流并在替换/卸载时取消，取消后回调不再写状态。动态对话按 id 重新挂载，避免上个对话的本地预览和输入状态混入。

### P2：附件上传和扫描轮询存在竞态

上传响应返回前可以发送消息，导致消息不带附件；旧扫描结果通过 `setFiles(fresh)` 能复活已经移除的附件或覆盖新附件。

上传期间禁用发送；轮询仅合并当前仍存在的附件，并丢弃失效 effect 的响应。增加浏览器测试，分别挂起上传/扫描响应来验证。

### P2：流资源和空响应处理不完整

S3 streaming body 在正常结束、异常或提前关闭时没有显式 close；Portal 的 SSE reader 没有释放，且通用 api 对 204 仍尝试解析 JSON。

现在在 finally 中释放资源，204 返回 undefined；新增两项 Portal 原生 Node 测试并接入 CI。

## 验证与基线

原始 macOS 基线有 4 项失败：GNU stat/find 与 BSD 命令差异导致 3 项，Prometheus 的 Linux `/proc` 指标导致 1 项。使用 GNU 工具运行沙箱 mock，保留预览错误用例所需的 find，同时仍从 PATH 排除 LibreOffice。仅在 Linux 上断言默认 process collector 指标，Linux CI 原有断言保留。

新增核心后端回归首轮 18 项全部失败，第二批配额/技能并发两项失败，UTC 用例失败；两个部署用例及两个 Portal 用例也均先观察到失败。随后修复并验证。

最终本地验证：

- SQLite + 真实 Redis：322 passed、8 skipped（PostgreSQL 专用分支），覆盖率 82.02%。
- PostgreSQL 16 + 真实 Redis：330 passed，包括迁移与跨进程锁语义测试。
- Chromium 浏览器 E2E：34 passed，含附件挂起响应、登录/退出、SSE、文件下载、个人技能与工作区预览。
- Portal 原生 Node 测试：2 passed；生产构建成功。
- Ruff lint/format、ShellCheck、bash 语法和 Python 锁文件一致性检查通过。

完整验证命令与维护注意事项见根目录 HANDOFF.MD。以上是本地结果，远端 CI 状态应以 PR 检查为准。

## 五个维度的结论

- 性能：移除列表 N+1 往返；文件哈希沿用分块读取；完成预签名上传增加一次存储内部复制，内存不随整个文件大小增长。每用户的配额临界区会串行化该用户的文件完成/产物提交，其中含存储 I/O；跨用户互不争用同一应用锁。SQLite 自身仍是单写者。
- 健壮性：在输入、上游结束标志、配额与部署失败处建立明确边界，依赖故障通过 HTTP 状态暴露。重试不改变已接受文件的内容。
- 可维护性：复用现有每用户锁和配额函数；UTC 和提示词校验收敛到响应/输入 schema。没有引入新运行时依赖或数据库迁移。
- 简单性：保留现有四服务分工与适配器，修复集中在实际边界；没有引入通用工作流框架或大规模重写。前端布局与产品说明文案不变。
- 可测试性：补足完整性、并发和延迟响应测试；部署分支使用命令替身，日常回归不依赖真实集群或付费模型。
